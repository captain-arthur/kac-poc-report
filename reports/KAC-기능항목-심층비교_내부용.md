# KAC 접근통제 요구항목 · 기능 심층 비교 (내부자용)

> 목적 ① — 금융감독원 감사 관점에서 **어떤 통제 항목이 필요한지** 카테고리·우선순위로 정의한다.
> 목적 ② — 각 항목을 **Teleport / Keycloak(자체개발)이 기능적으로 어떻게 지원하는지** 조사가 끝까지 완결되도록 정리한다.
> 성격 — 내부 검토용 **살아있는 문서**. 이해가 목적이므로 불확실은 숨기지 않고 `확인필요`+사유로 남긴다.
> ⚠️ 아래 요구항목 카테고리는 **일반적인 금융권 접근통제 감사 관점**으로 구성한 것이며, **사내 금감원 요건 문서와 대조·보정**해야 한다.

## 우선순위 범례
| 표기 | 의미 |
|---|---|
| ★핵심 | 감사 필수통제. 미충족 시 감사 지적·탈락 위험 |
| ●중요 | 보안·실무상 강하게 필요. 고위험 대상엔 사실상 필수 |
| ○부수 | 보완적. 있으면 유리 |

# 2부. 세부 설명 (★핵심 항목 심층)

## §2.1 kubeconfig 유출 방지 ★핵심

### 핵심 질문
> **"kubeconfig 파일이 유출되면 타인이 실제 사용자처럼 접근할 수 있는가?"**

### 답 (요약)
| 구성 | kubeconfig 파일만 유출 시 | 근거 |
|---|---|---|
| **Teleport — 표준 방식**(`tsh login`→`tsh kube login`) | **불가.** 파일엔 자격증명이 없고 `tsh` 자격(`~/.tsh`)이 있어야 함 | 원리 |
| **Teleport — 서명 발급**(`tctl auth sign`, CI/머신용) | **가능(TTL까지).** 인증서가 파일에 내장됨 | 실측 |
| **Keycloak(OIDC)** | **불가.** 파일엔 OIDC 설정만 있어 사용 시 Keycloak 재로그인(계정+MFA) 필요 | 원리 |

> 즉 "파일만 유출" 기준으로는 **Teleport 표준 방식과 Keycloak은 안전**, **Teleport 서명 발급 방식만 위험**하다. 서명 방식의 위험은 아래 완화수단으로 실효 차단된다(실측).

---
아래는 "파일 이상이 유출된 경우"와 "즉시 차단" 등 세부 시나리오다.

### 세부설명 ① — 자격증명(인증서/토큰)까지 유출된 경우
- **Teleport 서명 발급:** 내장 인증서는 **보유자 누구나 사용 가능**하고 요청마다 재인증이 없다. **동시접속도 가능.** 유효기간(TTL)까지 유효. — `실측`(발급 42분 후 타 위치에서 재인증 없이 재사용)
- **Keycloak 토큰 캐시 유출:** `id_token`은 **베어러 토큰** → 만료(보통 수 분)까지 사용 가능. `refresh_token`이 함께 유출되면 그 만료까지 새 id_token을 계속 발급 가능. **동시접속 가능.** — `원리` / `확인필요`(Keycloak PoC로 refresh 수명·동작 실측 필요)

### 세부설명 ② — 즉시 무효화(폐기) 가능 여부 ★ 결정적 차이
- **Teleport:** `tctl lock`으로 해당 사용자·세션을 **즉시 전역 차단**. 유출본이 있어도 그 즉시 `access denied`. — `실측`
- **Teleport(추가):** 역할에 `require_session_mfa`를 켜면 **MFA 검증이 없는 인증서(=유출 kubeconfig)는 즉시 거부**. — `실측`
- **Keycloak/OIDC:** kube-apiserver는 id_token의 **서명·만료만 검증**하고 매 요청마다 Keycloak에 되묻지 않는다. → **Keycloak에서 세션/계정을 폐기해도 이미 발급된 미만료 id_token은 만료 전까지 계속 유효**(즉시 무효화 공백). 완화책은 "id_token 수명을 매우 짧게". — `원리` / `확인필요`
- **정리:** *즉시 무효화* 관점에서 **Teleport가 구조적으로 유리**(Lock). Keycloak 경로는 토큰 수명 단축에 의존하는 한계가 있고, 이 지연폭은 PoC로 실측해야 한다.

### 세부설명 ③ — 동시접속(정당 사용자 로그인 중 유출본 사용)
- 두 솔루션 모두 **토큰/인증서 기반**이라, 유효한 자격증명 보유자는 정당 사용자와 **동시에** 접근 가능하다(요청별 재인증 없음). 차단은 위 ②(무효화)에 의존한다.
- 추가 방어: Teleport의 Device Trust(단말 바인딩)·IP pinning(Enterprise)으로 "발급된 단말/IP 외 사용 차단" 가능 → 유출본을 다른 단말에서 못 쓰게 함. — `확인필요`(Enterprise 미확보)

### 이 항목에서 남은 조사
- (Teleport) 표준 `tsh` 방식 kubeconfig 파일-only 유출 무력화 실측, Device Trust/IP pinning 실측(Enterprise).
- (Keycloak) 토큰 캐시 위치·id_token/refresh 수명·폐기 지연 실측(Keycloak PoC).

## §2.2 최소권한 RBAC ★핵심

### 핵심 질문
> **"사용자가 필요한 네임스페이스·동작(verb)만 접근하도록 강제되고, 과권한(cluster-admin 등)이 통제되는가?"**

### 답
- **Teleport:** 역할 `kubernetes_resources`(namespace/kind/verb)로 **프록시 계층에서 강제**. 하위 k8s 권한이 넓어도 Teleport가 좁힌다. `get ns`조차 접근 가능한 것만 노출(목록 필터링). — `실측`
- **Keycloak:** 인가는 **네이티브 k8s RBAC**(그룹→RoleBinding). Keycloak은 그룹만 제공. 중앙 강제·목록필터링·통합관리는 **개발필요**.

### 세부 사례
- **사례 A — 네임스페이스 격리:** viewer1(dev 전용)이 `prod` 조회 시도 → Teleport가 거부. — `실측`
- **사례 B — 읽기전용 강제:** viewer1이 `dev`에서 `delete` 시도 → verb 제한으로 거부. — `실측`
- **사례 C — 목록 필터링:** `kubectl get ns` 시 접근 가능한 `dev`만 노출(전체 네임스페이스 열람 불가). — `실측`
- **사례 D — 과권한/cluster-admin 금지:** `kubernetes_groups`를 `system:masters`가 아닌 제한 그룹에 매핑해 클러스터 관리자 권한이 자동 부여되지 않게 함. — `실측`(kac-view=view 바인딩) / deny 규칙으로 위험동작 배제는 `원리`
- **사례 E — 위험 동작 제어(exec/port-forward/secret 읽기):** exec·포트포워드·시크릿 접근 같은 고위험 동작을 역할에서 분리·차단. — `확인필요`(kubernetes_resources의 exec 제한 실측 필요)

### 감사 관점
- 감사관은 "권한 매트릭스(역할↔접근범위)"와 "cluster-admin 보유자 목록·근거"를 요구한다. Teleport는 역할 정의가 곧 매트릭스(코드화). Keycloak 경로는 각 클러스터 RBAC를 취합해야 함.

### 확인상태
T:실측(A~D)/exec제한 확인필요 · K:원리(중앙강제 개발필요)

## §2.3 접근/행위 감사로그 · 신원귀속 ★핵심

### 핵심 질문
> **"누가·언제·무엇을·어떤 리소스에 실행했는지 명령 단위로, 개인에게 귀속되어 남는가? 거부·관리자 행위도 남는가?"**

### 답
- **Teleport:** 모든 kube 호출을 `kube.request`(신원·verb·경로·리소스·네임스페이스, **거부 포함**)로, `kubectl exec`는 `exec`+`session.start/end`(**실행 명령**·컨테이너·노드)로 기록. — `실측`
- **Keycloak:** **인증 이벤트만**(로그인/토큰). kube 명령 단위 감사는 각 apiserver audit log 구성 + 중앙 수집 파이프라인 **개발필요**.

### 세부 사례
- **사례 A — 개인 귀속:** 감사 이벤트에 `login: viewer1`이 박힘(공용계정 아님). 프록시는 kube에 사용자를 impersonate하되 원 사용자를 로그에 보존. — `실측`
- **사례 B — 거부 기록:** 권한 없는 `prod` 접근 시도도 감사에 남아 "차단 이력"이 증적화됨. — `실측`
- **사례 C — 명령 캡처:** `kubectl exec ... -- sh -c '...'`의 **실제 명령 문자열**이 기록됨. — `실측`
- **사례 D — 관리자 행위:** 역할/사용자 생성 등 관리 행위가 `role.created`/`user.create`로 기록. — `실측`

### 감사 관점
- 감사관이 요구하는 전형: "특정 기간, 특정 인원의 prod 접근 이력 전부", "특권 명령 실행 내역", "권한 부여/변경 이력". Teleport는 단일 감사 스트림에서 산출 가능. Keycloak 경로는 인증로그+각 클러스터 apiserver 로그를 별도 상관분석해야 함(공백·수작업 위험).

### 확인상태
T:실측 · K:원리·개발필요

## §2.4 로그 무결성 · 보존기간 · 원격 전송 ★핵심

### 핵심 질문
> **"감사 로그가 위변조되지 않음을 보장하고, 규정 기간(예: 수년) 보존되며, 운영자가 임의 삭제하지 못하는가?"**

### 답 / 세부
- **위변조 방지:** 감사에서 흔히 요구되는 건 로그의 **불변성(WORM)** 또는 **무결성 검증**이다. Teleport 감사 이벤트/세션 기록은 백엔드(파일/S3 등)에 저장되며, 실무에서는 **S3 Object Lock(WORM)·외부 SIEM 실시간 반출**로 무결성을 확보한다. Teleport 자체의 이벤트 해시체인 여부·설정은 **실측 전**. — `확인필요`
- **보존기간:** 저장 백엔드의 보존정책에 종속 → 보존기간 설정·검증 필요. — `확인필요`
- **운영자 삭제 방지(직무분리):** 로그를 **접근 통제 시스템과 분리된 저장소(SIEM/WORM)**로 즉시 반출해 운영자가 원본을 지우지 못하게 하는 것이 정석. — `원리`
- **Keycloak 경로:** 로그 수집·보존·무결성 파이프라인을 **직접 설계·구현**해야 함(apiserver audit → 수집 → WORM/SIEM). — `개발필요`

### 감사 관점
- "로그 보존기간이 규정 이상인가", "운영자가 로그를 삭제/수정할 수 있는가", "로그가 원격/불변 저장되는가"는 감사 단골 지적 항목. **이 항목은 양 솔루션 모두 추가 확인/설계가 필요**하므로 우선 조사 대상.

### 확인상태
T:확인필요(무결성/보존 실측) · K:개발필요

## §2.5 특권 즉시 차단 (Lock / 강제 종료) ★핵심
### 핵심 질문
> **"보안사고·오남용·퇴직 시 특정 사용자의 모든 접근을 즉시 끊을 수 있는가? 진행 중 세션도 종료되는가?"**
### 답 / 세부 사례
- **Teleport:** `tctl lock`으로 즉시 전역 차단(모든 프로토콜/세션). 유출된 kubeconfig가 있어도 즉시 `access denied`. — `실측`
- **사례:** viewer1 Lock 직후 동일 kubeconfig 접근 → 즉시 차단, Lock 해제 후 복구. — `실측`
- **진행 중 세션 종료:** `disconnect_expired_cert` 및 Lock으로 세션 종료 유도 — 진행중 세션 강제종료 세부 동작은 `확인필요`.
- **Keycloak:** 세션 폐기는 가능하나 **미만료 id_token은 kube에서 계속 유효**(§2.1 ② 참조) → 즉시성 한계. — `원리`/`확인필요`
### 감사 관점
- "사고 발생 시 접근을 몇 분 내 차단 가능한가", "차단 이력이 기록되는가"를 확인. Teleport는 즉시 차단(강점), Keycloak은 토큰 수명에 의존(약점).
### 확인상태
T:실측 · K:원리·확인필요

## §2.6 특권/공용 계정 통제 · Break-glass ★핵심
### 핵심 질문
> **"root/cluster-admin 같은 특권·공용 계정 사용이 통제·기록되고, 비상(break-glass) 접근이 별도 승인·감사되는가?"**
### 답 / 세부
- **Teleport:** 접근이 항상 **개인 신원**으로 이뤄지고 kube에는 impersonation으로 전달 → 공용 계정 로그인 자체가 불필요. 특권 역할은 별도 정의·최소 인원, Access Requests로 일시 승격(§2.9). break-glass는 로컬 관리자 계정으로 분리·감사. — `실측(개인귀속)`/`원리(승격·break-glass)`
- **Keycloak:** 개인 인증은 제공하나, "특권 역할 일시 승격/비상 접근" 워크플로는 **개발필요**.
### 감사 관점
- "공용/특권 계정 목록과 사용 이력", "비상 접근 절차·승인·사후 검토"를 요구. 상시 특권계정 상주는 지적 대상 → JIT 승격(§2.9)과 연계.
### 확인상태
T:일부 실측+확인필요 · K:개발필요

## §2.7 직무분리 (SoD, Separation of Duties) ●중요~★핵심

## §2.14 접근 위치·시간 제한 · 단말 신뢰(Device Trust) ●중요
### 핵심 질문
> **"허용된 IP/네트워크·시간·등록 단말에서만 접근되는가? 유출 자격증명이 외부 단말에서 못 쓰이는가?"**
### 답
- **Teleport:** IP pinning(자격증명을 클라이언트 IP에 고정)·Device Trust(등록 단말만 허용)로 유출본의 외부 사용 차단. **Enterprise 전용.** — `확인필요(Enterprise)`
- **Keycloak:** IdP 조건부 정책(네트워크 등) 일부 가능하나 kube 접근 경로 강제는 **개발필요**.
### 감사 관점
- "접근 가능 위치·단말 제한 여부"를 확인. §2.1 유출 대응과 직접 연계.
### 확인상태
T:확인필요(Enterprise) · K:개발필요

## §2.15 전송·저장 암호화 · 비밀 관리 ★핵심(전송)/●중요(저장)
### 핵심 질문
> **"모든 접근 트래픽이 암호화되고, 저장된 자격·비밀이 안전하게 보호되는가?"**
### 답
- **Teleport:** 전 구간 TLS/mTLS(프록시). — `실측(TLS 연결)`. 저장 암호화·HSM은 Enterprise/백엔드 설정 → `확인필요`.
- **Keycloak:** OIDC/TLS 전송. DB 저장 암호화·시크릿 관리는 설계·설정 대상. — `원리`
### 감사 관점
- "전송구간 암호화(TLS 버전)", "저장 자격/비밀 암호화·키 관리"를 확인.
### 확인상태
T:실측(전송)/저장 확인필요 · K:원리

## §2.16 감사 증적 산출(리포팅) ★핵심(감사 대응 실무)
### 핵심 질문
> **"감사 시 요구되는 '누가 무엇에 접근 가능한가(권한 현황)'와 '실제 접근/승인 이력'을 신속히 산출할 수 있는가?"**
### 답 / 세부
- **Teleport:** 권한 현황은 역할/사용자 정의(코드)로 산출, 접근/명령 이력은 단일 감사 스트림·세션 목록에서 조회·반출. 정형 리포트 양식은 SIEM/조회로 구성. — `원리`/일부 `실측(이벤트 조회)`
- **Keycloak:** 인증 이력은 Keycloak, 접근/명령 이력은 각 클러스터 로그를 취합해야 함 → 통합 리포트는 **개발필요**.
### 감사 관점
- 감사관은 짧은 시간에 "권한 매트릭스", "기간별 접근 이력", "승인 이력"을 요구한다. **한 곳에서 산출되는지**가 감사 대응 공수를 좌우.
### 확인상태
T:원리/일부 실측 · K:개발필요
