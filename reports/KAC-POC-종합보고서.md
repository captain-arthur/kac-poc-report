# KAC 접근제어 도입 POC 종합 보고서 (초안)
### Teleport vs Keycloak(자체개발) 비교 검증

---

## 결론 먼저 (한눈에 보기)

**KAC의 Hela 대체를 위해 두 방향 — ① 솔루션 도입(Teleport) ② 자체개발(Keycloak 기반) — 을 동일한 7개 기준으로 검증했다. 현재까지의 객관적 결과는 다음과 같다: Teleport는 접근제어·감사의 핵심 통제 대부분을 제품 기능으로 즉시 충족하며(일부 심화 통제는 Enterprise 라이선스 확보 후 실측 예정), Keycloak 기반 자체개발은 인증(SSO·MFA)은 강점이지만 Kubernetes 접근 강제·감사·세션 레코딩·프록시 등 KAC의 본질 기능 대부분을 직접 개발해야 한다.**

### 최종 정리표

| 구분 | 내용 |
|---|---|
| **검증 질문** | Hela를 대체해 금융감사를 통과할 접근제어를, "솔루션(Teleport)"과 "자체개발(Keycloak)" 중 무엇으로 하는 것이 현실적인가? |
| **현재까지 관찰** | Teleport = 감사 핵심 통제를 **제품이 기본 제공** / Keycloak = **인증만 제공**, 나머지는 대부분 자체개발 필요 |
| **감사 필수통제** | Teleport로 충족 가능(SSO·승인·접근검토·세션기록·Lock). Keycloak은 인증 외 통제를 개발로 메워야 함 |
| **비용 구조** | Teleport = 라이선스 구독 + 운영 / Keycloak = 라이선스 0 + **대규모 개발공수 + 운영** |
| **최종 권고** | (잠정) 솔루션(Teleport) 우위. **단, Enterprise 실측 + Keycloak PoC 완료 후 확정** |
| **의사결정 요청** | ① Teleport **Enterprise 평가 라이선스** 확보 ② Keycloak 자체개발 PoC 범위·기간 승인 |

### 후보 비교 요약 (7개 영역, 한 줄 판정)

| 영역 | Teleport (솔루션) | Keycloak (자체개발) |
|---|---|---|
| 1. 인증 | 개인계정·MFA·SSO 충족 (SSO는 Enterprise 검증예정) | SSO·MFA 강점(핵심 기능) |
| 2. 인가 | k8s RBAC 최소권한 **제품 강제** (실측) | 앱 역할만; **k8s 접근 강제는 개발 필요** |
| 3. 세션 | 단기인증서·유휴타임아웃·kubectl 연동 충족(실측) | 토큰 만료 존재; k8s 세션 통제는 개발 |
| 4. 감사 | kube 명령 감사·세션레코딩·Lock 충족(실측) | 인증 이벤트만; **kube 감사·레코딩 개발 필요** |
| 5. 운영 | 셀프호스트 가능; HA는 Enterprise | 셀프호스트·HA 가능; **전면 내부 유지보수** |
| 6. 전환 | 멀티클러스터·kubeconfig 대체 충족 | 프록시·멀티클러스터 연동 개발 필요 |
| 7. 비용 | 라이선스 구독(유료) | 라이선스 0, **개발·운영 공수 큼** |

> 상세 근거와 판정 사유는 아래 3장, Teleport 실측 원문은 별첨 참조. 결론만 필요하면 여기까지.

## 1. 목적 · 범위 · 후보

### 1.1 결정할 질문
> Hela를 대체해 금융감사를 통과할 KAC 접근제어를, **솔루션 도입(Teleport)** 과 **자체개발(Keycloak 기반)** 중 어느 방향으로 추진하는 것이 필수 통제·비용·운영책임 측면에서 가장 현실적인가?

### 1.2 후보(도입안)
- **후보 A — Teleport:** 상용 접근제어 플랫폼. 본 POC는 **현 시점 검증 가능한 CE로 1차 실측**, 심화 통제는 **Enterprise 라이선스 확보 후 실측 예정**.
- **후보 B — Keycloak 기반 자체개발:** Keycloak(오픈소스 IAM)을 인증 축으로, RBAC 연동·프록시·감사·세션 통제를 **내부 개발**하여 구성.

### 1.3 범위
- 포함: 인증 / 인가 / 접속·세션 / 감사·내부통제 / 운영 / 전환 / 비용의 7개 영역.
- 제외: 회사 표준 RBAC 모델 정의(별도 과제). 단, 정의된 정책의 적용·회수·감사 능력은 평가.
- 후속: QueryPie·HIWARE는 동일 기준으로 추가 비교 예정.

---

## 2. 평가 방법

- **필수조건 우선:** 감사·보안·핵심 사용성 필수통제는 다른 장점으로 상쇄하지 않는다.
- **사실/주장 분리:** 판정마다 근거와 **검증 상태**를 명시한다.

**검증 상태 범례**
| 표기 | 의미 |
|---|---|
| `실측` | 본 POC 환경에서 직접 확인 (Teleport는 현재 CE로 확인) |
| `Enterprise 검증예정` | 제품은 지원하나, 라이선스 확보 후 실측 필요 |
| `문서확인` | 공식 문서/기능 매트릭스로 확인 |
| `개발필요` | 해당 후보에서 자체 개발·연동이 있어야 충족 |

**판정 기준**
| 판정 | 기준 |
|---|---|
| 충족 | 추가 개발 없이 요구사항 충족(해당 검증 상태로 확인) |
| 부분 충족 | 제약·수작업·추가 설정/연동/개발이 필요 |
| 미확인 | 아직 검증 전 (검증 상태에 따라 후속 확인) |

## 3. 후보 비교표 (영역별 상세)

> 형식: **판정 · (검증상태)**

### 3.1 인증 (Authentication)
| 통제 항목 | Teleport | Keycloak(자체개발) |
|---|---|---|
| 개인 식별 계정(공용계정 배제) | 충족 · 실측 | 충족 · 문서확인 |
| MFA(2FA, OTP/WebAuthn) 강제 | 충족 · 실측 | 충족 · 문서확인(핵심 기능) |
| 기업 IdP SSO(SAML/OIDC) | 충족 · Enterprise 검증예정 | 충족 · 문서확인(Keycloak 자체가 IdP) |

### 3.2 인가 및 권한관리 (Authorization)
| 통제 항목 | Teleport | Keycloak(자체개발) |
|---|---|---|
| Kubernetes RBAC 최소권한(namespace·verb) | 충족 · 실측 | 부분 · 개발필요(kube 접근 강제 계층 구축) |
| 접근 가능 리소스만 노출(목록 필터링) | 충족 · 실측 | 부분 · 개발필요 |
| JIT 임시권한 + 승인 워크플로 | 충족 · Enterprise 검증예정 | 부분 · 개발필요(워크플로 구축) |
| 주기적 접근검토(Access Reviews) | 충족 · Enterprise 검증예정 | 부분 · 개발필요(그룹관리는 있으나 검토 프로세스 개발) |

### 3.3 접속·세션관리 및 사용자 경험
| 통제 항목 | Teleport | Keycloak(자체개발) |
|---|---|---|
| 짧은 수명 인증서 / 세션 TTL | 충족 · 실측 | 부분 · 개발필요(k8s 접근에 매핑) |
| 유휴 세션 타임아웃 | 충족 · 실측 | 부분 · 개발필요 |
| 표준 도구 연동(kubectl/lens/k9s) | 충족 · 실측(프록시 경유) | 부분 · 개발필요(OIDC kube 연동 + 편의계층) |
| 세션 참관·강제종료(Moderated) | 충족 · Enterprise 검증예정 | 미지원 · 개발필요 |
| IP 기반 접근 제한 | 충족 · Enterprise 검증예정 | 부분 · 개발필요 |

### 3.4 감사 및 내부통제 (Audit) — 감사 대응 핵심
| 통제 항목 | Teleport | Keycloak(자체개발) |
|---|---|---|
| 구조화 감사로그(who·what·verb·resource) | 충족 · 실측 | 부분 · 개발필요(인증 이벤트만; kube 명령 감사는 프록시 개발) |
| 명령/세션 레코딩(kube exec) | 충족 · 실측 | 미지원 · 개발필요 |
| 세션/신원 Lock(즉시 차단) | 충족 · 실측 | 부분 · 개발필요(세션 무효화 존재, 전역 즉시차단은 개발) |
| SIEM 내보내기 | 충족 · 문서확인 | 충족 · 문서확인(Event SPI) |
| 자동 이상탐지/Access Monitoring | 충족 · Enterprise 검증예정 | 미지원 · 개발필요 |

### 3.5 운영 및 유지보수
| 통제 항목 | Teleport | Keycloak(자체개발) |
|---|---|---|
| 셀프호스트 배포 | 충족 · 실측 | 충족 · 문서확인 |
| 고가용성(HA)/다중지역 | 충족 · Enterprise 검증예정 | 충족 · 문서확인(클러스터링) |
| 유지보수 주체·부담 | 벤더 지원 + 내부 운영 | **전면 내부(개발+운영)** |

### 3.6 전환 및 실제 사용
| 통제 항목 | Teleport | Keycloak(자체개발) |
|---|---|---|
| 멀티 클러스터 등록 | 충족 · 실측(에이전트) | 부분 · 개발필요 |
| 기존 kubeconfig 접근 대체 | 충족 · 실측 | 부분 · 개발필요(OIDC kubeconfig) |
| Hela 병행운영·컷오버·롤백 | 미확인(전환계획 별도) | 미확인(전환계획 별도) |

### 3.7 비용 및 지속 가능성
| 통제 항목 | Teleport | Keycloak(자체개발) |
|---|---|---|
| 직접비(라이선스) | 유료(Enterprise 구독) | 0(오픈소스) |
| 개발비(초기) | 낮음(제품 기능 활용) | **높음**(프록시·RBAC·감사·세션 개발) |
| 운영비(지속) | 구독 + 셀프호스트 운영 | 내부 운영 + 개발 유지보수 |
| 벤더 종속 | 있음(계약·이탈비용) | 없음(내부 통제) |

## 4. 자체개발(Keycloak) 시 필요한 추가 개발 범위 (요약)

Keycloak은 "인증(로그인·SSO·MFA)"을 제공하지만, KAC의 본질인 **"Kubernetes 접근을 통제·기록·감사"** 하는 기능은 없다. 자체개발 시 아래를 직접 구축해야 한다.

| 구성요소 | 필요 이유 | 난이도(개략) |
|---|---|---|
| 접근 프록시(kube API 게이트웨이) | 사용자별 인가·세션·감사를 강제할 지점 | 높음 |
| Keycloak 그룹/역할 ↔ k8s RBAC 매핑·회수 | 인증 결과를 접근권한으로 변환 | 중 |
| 감사로그 수집·정규화·보존(무결성) | 금감원 감사 증적 | 높음 |
| 세션 레코딩(kube exec) | 감사·사후조사 | 높음 |
| 승인 워크플로·주기적 접근검토 | 감사 필수통제 | 중~높음 |
| 다중 클러스터 연동·운영도구(관리 UI 등) | 실사용성 | 중 |

> 위 항목은 사실상 **Teleport/Hela가 제공하는 기능을 재구현**하는 것에 해당한다. 정확한 인력·기간은 별도 산정 필요.

## 5. 비용·기간·위험 (방향성 판단용)

- **솔루션(Teleport):** 초기 개발 최소, 감사 통제 즉시 확보. 반복 구독비 + 벤더 종속 감수. 심화 통제는 Enterprise 라이선스 필요.
- **자체개발(Keycloak):** 라이선스비 0이나, 프록시·감사·세션·승인 등 **KAC 핵심을 재구현**해야 하며 개발기간·유지보수 부담과 감사 통과까지의 리스크가 크다.
- **공통 리스크:** Hela 전환(병행운영·컷오버·롤백) 계획은 두 방향 모두 별도 필요.

## 6. 최종 권고 및 다음 단계

### 6.1 잠정 권고
현재까지의 객관적 검증 결과, **솔루션(Teleport) 방향이 감사 통과·개발부담·기간 면에서 우위**로 관찰된다. 다만 다음 두 검증을 완료한 뒤 최종 확정한다.

### 6.2 다음 단계 (확정을 위한 남은 검증)
1. **Teleport Enterprise 실측(라이선스 필요):** SSO(SAML/OIDC) · 승인 워크플로 · 주기적 접근검토 · Moderated Session · HA — 본 보고서에서 `Enterprise 검증예정`으로 표기한 항목.
2. **Keycloak 자체개발 PoC:** 4장의 추가 개발 범위에 대한 **최소 기능 시제(프록시+RBAC 매핑+감사)** 로 실현 가능성·공수 실측.
3. **QueryPie/HIWARE** 동일 기준 비교 후 종합.

### 6.3 권고 채택 시 받아들여야 할 단점
- 솔루션 채택은 라이선스 비용·벤더 종속 수반.
- 자체개발 채택은 개발기간·유지보수 부담과 감사 통과 리스크 수반.
